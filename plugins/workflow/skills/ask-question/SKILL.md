# ask-question

ユーザーの計画・設計・要件をインタビューし、共通認識に到達するまで質問を重ねるスキル。

表面的に2〜3問聞いて切り上げると、暗黙の前提が残ったまま実装に進み手戻りになる。それを防ぐため、未解決の確認事項がゼロになるまでループする（停止条件は「終了条件」節）。

## 全体の流れ

```
1. 決定ツリーを組み立て、未解決項目チェックリストをファイルに書く
2. 上流の未解決項目を1つ選び、AskUserQuestion で問う
3. 回答を記録し、チェックリストを更新（解決済みにチェック / 新たに派生した分岐を追加）
4. 未解決項目が残っていれば 2 に戻る ← ここがループ
5. 未解決項目ゼロ、または「もう十分」 → ループ停止 → サマリ出力 → チェックリスト削除
```

## 自動ループの仕組み（loop連携）

このスキルは「確認事項が尽きるまで自分自身を回し続ける」ループとして動く。実装上は2層で担保する。

### ターン内ループ（通常はこれで完結）

`AskUserQuestion` はユーザーの回答が返るまでその場でブロックする。だから1ターンの中で「問う→回答を得る→次を問う」を連続実行できる。**未解決項目が残っている限り、同一ターン内で次の `AskUserQuestion` を出し続ける**のが基本。途中で平文の感想や中間まとめを挟んでターンを終えてはいけない（ループが途切れる原因になる）。

### ウェイクアップによるループ保証（離脱・中断への保険）

ユーザーが席を外した、あるいは何らかの理由でターンが終了してしまった場合に**未解決項目が残ったまま 認識合わせが立ち消えになる**のを防ぐため、`ScheduleWakeup` でループを再起動できるようにしておく。

- **ターンを終える時点で未解決項目が残っている場合は、必ず `ScheduleWakeup` を呼ぶ。**
  - `prompt`: `/workflow:ask-question`（このスキルを再起動し、**自セッションの**チェックリスト（セッション固有パス）の続きから再開させる。他セッションのチェックリストは読まない）
  - `delaySeconds`: `1200`（20分。対話の保険なので頻繁にポーリングする必要はなく、キャッシュも無駄にしない）
  - `reason`: 「未解決の確認事項が N 件残っているため再開」など具体的に
- **未解決項目がゼロ、またはユーザーが明示的に離脱した場合は `ScheduleWakeup` を呼ばない。** これがループの停止条件であり、停止は「呼ばない」という明示的な行為で表現する。

再起動時はチェックリストを読み、**タイトルが自分の依頼と一致する場合のみ**解決済みを除いた未解決項目の続きから再開する。不一致なら再開せず、別タスクのチェックリストには手を付けない。

## 状態保持: 未解決項目チェックリスト

ウェイクアップをまたいでも状態を失わないよう、決定ツリーの進捗を**ファイルに永続化**する。

- 保存先: タスク/セッション固有パス。固定の共有パスは使わない。第一候補は scratchpad ディレクトリ（セッション固有）の `ask-question-checklist.md`。無い場合のフォールバックは `/tmp/ask-question-checklist-<session-id>.md`。
- 形式: Markdown のチェックリスト。各項目に「論点・現時点の推奨・依存（どの項目の回答待ちか）」を併記

```markdown
# 認識合わせチェックリスト: <依頼の一言要約>

## 未解決
- [ ] 永続化方式（RDB / KVS）— 推奨: RDB（既存がPostgres）/ 依存: なし（上流）
- [ ] スキーマ設計 — 依存: 永続化方式の確定待ち

## 解決済み
- [x] スコープ: ユーザー認証のみ。管理画面は対象外（2026-06-16 確認）
```

各サイクルでやること:

1. ファイルを読む。読めたら先頭タイトル `# 認識合わせチェックリスト: <依頼要約>` が**今回の依頼と一致するか照合する**。一致 → 続行。不一致 or ファイルなし → 既存は読まず・消さず、今回の依頼で新規作成する（既存は別タスク/別セッションが使用中の可能性があるため触れない）。
2. 「未解決」のうち依存が解けている最上流の項目を1つ選ぶ。
3. `AskUserQuestion` で問う。
4. 回答を「解決済み」に移し、回答日と決定内容を残す。回答によって新たな分岐が生まれたら「未解決」に追加する。実装中に判断できる粒度の項目は、問わずに「実装時に判断」と注記して解決済みに移してよい（瑣末な質問でループを引き延ばさない）。
5. 「未解決」が空になったら、サマリ出力後にファイルを削除する。

ファイルは作業の途中経過であり、最終成果物ではない。完了時に必ず消す。

## 質問は AskUserQuestion ツールで行う

このスキルが起動している間、ユーザーへの確認は**必ず `AskUserQuestion` ツール**で行う。平文で「Aですか？Bですか？」と並べて聞くのは禁止。理由:

- 構造化された選択肢にすることで、ユーザーの判断負荷が下がる
- 推奨案を選択肢の先頭に置き、ラベル末尾に「(Recommended)」を付けると意思決定が速くなる
- 「Other」で自由入力もできるため、想定外の意図も拾える

各質問について:

- 各質問では**あなたの推奨回答（と理由）を必ず提示**してから問う
- 選択肢は2〜4個に絞る（多すぎると選びにくい）
- 推奨案を**先頭**に置き、ラベルに `(Recommended)` を付ける
- 各選択肢の `description` に「選んだ場合に何が起きるか・トレードオフ」を1〜2行で書く
- 複数選択が自然な観点（例: 「どの機能を含める？」）では `multiSelect: true` を使う
- `header` は12文字以内のチップ表示用ラベル（例: 「DB方式」「認証方式」）

質問は**原則1度に1つ**。回答に応じて次の質問を組み立てる。ただし複数の論点が**並列で独立**しているとき（互いに依存しない）は、`questions` 配列に最大4つまでまとめてよい。依存関係がある場合は1問ずつ。

## コードベースで答えられる質問はコードを読む

「現状の実装はどうなっているか」「このクラスはどこで使われているか」「設定値の現在の値は何か」など、**コードベースの探索で答えが出る質問はユーザーに聞かない**。Grep / Read / Glob で先に調べ、判明した事実を前提として次の質問に進む。

ユーザーの時間は有限。AI で完結できる調査を肩代わりしてもらうのは無駄であり、これをやらないとループが「本来聞かなくてよい質問」で膨らみ、いつまでも終わらなくなる。

## 何を詰めるか（観点リスト）

依頼内容に応じて取捨選択。すべて聞く必要はないが、重要な分岐を見逃さない。チェックリストの初期項目を組み立てる材料にする。

- **目的・ゴール**: なぜそれをやるのか、成功条件は何か
- **スコープ**: 何を含め、何を含めないか
- **影響範囲**: グローバル/プロジェクト/モジュール/ファイル単位
- **成果物の形式**: ファイル形式、出力先、命名規則
- **実装方針**: アーキテクチャ、設計パターン、責務分割
- **技術選定**: ライブラリ、フレームワーク、ミドルウェア
- **データモデル**: エンティティ、関係、永続化方式
- **エラー処理方針**: 例外の扱い、リトライ、ロールバック
- **非機能要件**: 性能、可用性、セキュリティ、運用
- **互換性**: 既存資産への影響、後方互換性の要否
- **テスト戦略**: 単体/統合/E2E、カバレッジ目標
- **リリース方針**: 段階展開、フィーチャーフラグ、ロールバック手順

## 終了条件（ループ停止）

次のいずれかでループを止める。止めるときは `ScheduleWakeup` を呼ばず、サマリを出力し、チェックリストファイルを削除する。

- **未解決項目がゼロになった**（チェックリストの「未解決」が空）
- **ユーザーが「もう十分」「実装に進んで」など明示的に離脱した**

## 最終アウトプット

詰め切ったら、決まったことを Markdown の箇条書きでまとめて提示する。後続の実装ステップ（プラン作成、コーディング、ドキュメント化など）に直接渡せる粒度で。チェックリストの「解決済み」がそのまま素材になる。

## 設計上の注意

- **推測で進めない**: 「たぶんこうだろう」で次に進むと手戻りの元。実装に影響する曖昧な点は確認する（些末な点は各サイクルの手順 4 に従う）
- **誘導しない**: 推奨案は明示するが、ユーザーが別案を選んでも受け入れる
- **判断どうしの絡みまで確かめる**: 表面的な合意で終わらせず、その判断が他の決定とどう絡むかまで踏み込む
- **テンポを維持**: 1問が重すぎると進まない。サクサク聞ける粒度に分解する
- **止めるのは終了条件を満たしたときだけ**: 未解決項目を残したまま「だいたい分かった」で切り上げると、暗黙の前提が残って手戻りになる
