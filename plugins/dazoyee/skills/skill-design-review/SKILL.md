# Skill Design Review

Agent-First な5つの設計パターンに基づくスキル設計のレビュー・ガイドスキル。

出典: Google Workspace CLI（gws）の89スキルから抽出された設計パターン。
詳細リファレンス: このスキルディレクトリの `references/design-patterns.md`

---

## モード判定

以下の基準でモードを自動判定する:

| 条件 | モード |
|---|---|
| 既存の SKILL.md パスが指定されている | レビューモード |
| 「レビュー」「チェック」「確認」「改善」が含まれる | レビューモード |
| 「新しいスキル」「作りたい」「設計したい」が含まれる | ガイドモード |
| 判断できない場合 | ユーザーに確認する |

---

## レビューモード

### 入力

- 対象スキルの SKILL.md パス（指定がない場合はユーザーに確認）
- 複数スキルの一括レビューも可（ディレクトリ指定 or `~/.claude/skills/` 全体）

### 手順

#### Phase 1: 読み取り・分析（読み取り専用）

1. `references/design-patterns.md` を読み込む
2. 対象の SKILL.md を読み込む
3. 5パターンの各観点で分析する（下記スコアリング基準参照）
4. レビューレポートを生成してユーザーに提示する

#### Phase 2: 改善適用（ユーザー確認後）

5. ユーザーが改善を希望する項目を確認する
6. 該当箇所を修正する
7. 修正後の SKILL.md を提示する

### スコアリング基準

各パターンを 0-2 の3段階で評価する:

| スコア | 意味 | 基準 |
|---|---|---|
| 2 | 適合 | パターンの要件を満たしている |
| 1 | 部分適合 | 一部は満たしているが改善余地がある |
| 0 | 非適合 | パターンの要件を満たしていない、または該当するが対応していない |
| - | 対象外 | このパターンが適用される状況にない（スコア計算から除外） |

### 5パターンの評価観点

#### 1. 3層分離（関心分離）

- スキルの責務は単一か
- 操作定義・行動指針・手順が混在していないか
- 依存方向は一方向か

#### 2. 宣言的インターフェース（フロントマター）

- `name` が kebab-case で定義されているか
- `description` が具体的でトリガー条件を含むか
- 依存関係（ツール・スキル・MCP サーバー）が明示されているか

#### 3. ヘルパー（80/20ルール）

- 頻出操作が明確に定義されているか
- 各操作の必須パラメータが明示されているか
- 安全なデフォルト値が設定されているか
- 操作名から意図が一意に特定できるか

#### 4. ガードレール

- 破壊的操作に対するガードレールがあるか
- 禁止/確認/安全デフォルト/スコープ制限のパターンで記述されているか
- ガードレールの記述が明確でエージェントが解釈に迷わないか

#### 5. inspect-then-call

- 破壊的操作を含む場合、読み取り専用フェーズと実行フェーズが分離されているか
- Phase 1 が「読み取り専用」と明示されているか
- Phase 2 の前にユーザー確認が組み込まれているか

### レビューレポートフォーマット

```markdown
# スキル設計レビュー: <スキル名>

## サマリー

| # | パターン | スコア | 判定 |
|---|---|---|---|
| 1 | 3層分離 | 2/2 | 適合 |
| 2 | 宣言的IF | 1/2 | 部分適合 |
| 3 | ヘルパー | -  | 対象外 |
| 4 | ガードレール | 0/2 | 非適合 |
| 5 | inspect-then-call | 1/2 | 部分適合 |

**総合スコア: X / Y**（対象外を除く）

## 詳細

### パターン1: 3層分離
**スコア: 2/2（適合）**
- 評価: <具体的な評価内容>

### パターン2: 宣言的インターフェース
**スコア: 1/2（部分適合）**
- 評価: <具体的な評価内容>
- 改善提案: <具体的な改善案>

...（各パターンについて同様）

## 改善提案まとめ

1. <優先度の高い改善提案>
2. <次に優先度の高い改善提案>
...
```

## ガイドモード

### 入力

- 作りたいスキルの概要・目的（ユーザーとの対話で明確化）

### 手順

#### Step 1: 要件の明確化

ユーザーに以下を確認する:

1. **スキルの目的**: 何を達成するスキルか
2. **トリガー条件**: どのような発話・状況でトリガーされるか
3. **破壊的操作の有無**: データ変更・ファイル削除・メッセージ送信等を含むか
4. **依存関係**: 使用するツール・MCP サーバー・他スキルはあるか

#### Step 2: パターン適用の判断

要件に基づき、5パターンの適用方針を決める:

| パターン | 適用基準 |
|---|---|
| 3層分離 | 常に意識する。1つのスキルに複数の責務を混在させない |
| 宣言的IF | 常に適用する。フロントマターは必須 |
| ヘルパー | 複数の操作パターンがある場合に適用 |
| ガードレール | 破壊的操作を含む場合に必須 |
| inspect-then-call | 破壊的操作を含む場合に必須 |

#### Step 3: SKILL.md の生成

`references/design-patterns.md` のテンプレートを参考に、パターンに沿った SKILL.md を生成する。

#### Step 4: レビュー

生成した SKILL.md に対してレビューモードを実行し、5パターンへの適合を確認する。

---

## 制約

- **読み取り専用フェーズの厳守**: レビューモードの Phase 1 では SKILL.md を変更しない
- **ユーザー確認の必須化**: 改善の適用前に必ずユーザーの承認を得る
- **リファレンス参照**: 評価基準は `references/design-patterns.md` に従う。独自の基準を追加しない
- **スコアリングの客観性**: 曖昧な評価を避け、チェック項目に基づいて判定する
