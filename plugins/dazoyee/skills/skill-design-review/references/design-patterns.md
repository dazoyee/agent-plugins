# Agent-First スキル設計パターン リファレンス

Google Workspace CLI（gws）の89スキルから抽出された5つの設計パターン。
スキルのレビュー・設計ガイドの判定基準として使用する。

出典: [Google Workspace CLI（gws）](https://github.com/googleworkspace/cli) のスキル群を調査して抽出した

---

## パターン1: 3層アーキテクチャ（関心分離）

### 原則

スキルの責務を3つの層に分離する。各層は異なる抽象度を持ち、依存方向は上位→下位の一方向のみ。

| 層 | gws での名称 | AIエージェントでの対応 | 責務 |
|---|---|---|---|
| 操作層 | サービス層（gws-*） | MCPツール定義 | 個別APIの操作定義 |
| 行動層 | ペルソナ層（persona-*） | エージェント定義 | ロール別の行動指針 |
| 手順層 | レシピ層（recipe-*） | スキル定義 | 複数ツールを組み合わせた手順 |

### チェック項目

- [ ] スキルの責務は単一か（操作定義・行動指針・手順が1ファイルに混在していないか）
- [ ] 依存方向は一方向か（手順→操作、行動→操作。逆方向の依存はないか）
- [ ] 1つのスキルが複数の層にまたがっていないか

### 良い例

```markdown
# recipe-meeting-prep（手順層のみ）
## 手順
1. Calendar でスケジュールを取得
2. Drive で関連資料を検索
3. 結果をまとめて報告
```

操作定義（Calendar API の呼び方）は別のサービススキルに委譲している。

### 悪い例

```markdown
# meeting-prep
## Calendar API の使い方
gws calendar events list --calendar primary ...
## 行動指針
朝はスタンドアップレポートから始める
## 手順
1. スケジュールを取得して...
```

操作定義・行動指針・手順が1ファイルに混在している。

### 改善テンプレート

責務が混在している場合、以下の基準で分離を検討する:

- **操作定義**が含まれている → MCPツール定義またはサービススキルに切り出す
- **行動指針**が含まれている → エージェント定義に切り出す
- **手順**のみが残る → それがスキルの本来の責務

## パターン2: 宣言的インターフェース（SKILL.md フロントマター）

### 原則

スキルのメタデータ・依存関係をYAMLフロントマターで宣言的に定義する。本文を読まなくても「何ができるか」「何に依存するか」が分かる状態にする。

### チェック項目

- [ ] フロントマターに `name` が定義されているか
- [ ] フロントマターに `description` が適切に定義されているか（トリガー条件を含む）
- [ ] 依存するツール・スキル・MCPサーバーが明示されているか（本文中に散在していないか）
- [ ] description にトリガーとなるキーワード・フレーズが含まれているか

### 良い例

```yaml
---
name: research
description: |
  特定のトピックを深く調査し、構造化されたMarkdownレポートを生成するスキル。
  以下の場合に使用:
  - 「〇〇を調査して」「〇〇について調べて」
  - /research コマンド
---
```

name、description、トリガー条件が明確。

### 悪い例

```yaml
---
name: my-skill
description: いろいろなことをするスキル
---
```

description が曖昧でトリガー条件が不明。依存関係も不明。

### 改善テンプレート

```yaml
---
name: <スキル名（kebab-case）>
description: |
  <1文で何をするスキルか>。
  <補足説明（任意）>。
  以下の場合に使用:
  - <トリガーとなるユーザー発話パターン1>
  - <トリガーとなるユーザー発話パターン2>
  - /<コマンド名>
---
```

## パターン3: ヘルパーコマンド（80/20ルール）

### 原則

80%の頻出ユースケースを明確に定義されたヘルパーとしてカバーする。残りの高度な操作はraw APIに委譲する。ヘルパーは「意図が一意に特定できる名前」「必須パラメータの明示」「安全なデフォルト値」を持つ。

### チェック項目

- [ ] 頻出操作が明確に定義されているか（名前・手順・パラメータ）
- [ ] 各操作の必須パラメータが明示されているか
- [ ] 安全なデフォルト値が設定されているか（推測の余地がない）
- [ ] 操作名から意図が一意に特定できるか
- [ ] 低レベルの実装詳細がエージェントから隠蔽されているか

### 良い例

```markdown
## +send ヘルパー
メールを送信する。

### 必須パラメータ
- `--to`: 送信先メールアドレス
- `--subject`: 件名
- `--body`: 本文

### デフォルト動作
- Content-Type: text/plain（HTMLが必要な場合は --html フラグ）
- RFC 2822フォーマットは自動処理
```

### 悪い例

```markdown
## メール送信
gws gmail messages send コマンドを使ってメールを送信できます。
パラメータについては --help を参照してください。
```

必須パラメータが不明。エージェントが推測する余地がある。

### 改善テンプレート

頻出操作ごとに以下を定義する:

```markdown
## <操作名>
<1文で何をするか>

### 必須パラメータ
- `<パラメータ名>`: <説明>

### オプション
- `<パラメータ名>`: <説明>（デフォルト: <値>）

### 注意事項
- <安全性に関する制約>
```

## パターン4: 4レベルガードレール

### 原則

ガードレールを階層化し、「全体に適用すべき制約」と「特定の操作にのみ適用すべき制約」を明確に分離する。

| レベル | 対応ファイル | 適用範囲 | 強度 |
|---|---|---|---|
| 共有 | グローバルルール（CLAUDE.md等） | 全スキル横断 | 最強 |
| サービス固有 | ツール別ルール | 操作単位 | 強 |
| ワークフロー固有 | スキル別制約 | 特定手順内 | 明示的 |
| ペルソナ固有 | エージェント別制約 | 文脈依存 | 文脈依存 |

### 4つのガードレールパターン

| パターン | 記述形式 | 例 | 効果 |
|---|---|---|---|
| 禁止 | "Never ..." / "〜禁止" | "Never output secrets" | 例外なく適用される不変条件 |
| 確認 | "Always confirm ... before ..." | "Always confirm write/delete" | 破壊的操作前に人間の介入を強制 |
| 安全デフォルト | "Use ..." / "デフォルトで〜" | "Use --dry-run for destructive operations" | 非破壊モードをデフォルト化 |
| スコープ制限 | "Read-only" / "読み取り専用" | "Read-only -- never modifies data" | 操作範囲を読み取りに限定 |

### チェック項目

- [ ] 破壊的操作（ファイル削除・データ変更・メッセージ送信等）に対するガードレールがあるか
- [ ] ガードレールが適切なレベルに配置されているか（全体に適用すべきものがスキル内にのみ記載されていないか）
- [ ] 禁止・確認・安全デフォルト・スコープ制限のいずれかのパターンで記述されているか
- [ ] ガードレールの記述が曖昧でなく、エージェントが解釈に迷わない表現か

### 良い例

```markdown
## 安全性ルール
- **禁止**: APIキー・トークンを出力に含めない
- **確認**: 書き込み・削除操作は常にユーザー確認を取る
- **安全デフォルト**: 破壊的操作前にドライランを実行する
- **スコープ制限**: このフェーズでは読み取り専用
```

### 悪い例

```markdown
## 注意事項
気をつけて操作してください。
重要なデータは削除しないようにしましょう。
```

曖昧で、エージェントが具体的にどう行動すべきか判断できない。

## パターン5: inspect-then-call（2段階安全設計）

### 原則

破壊的操作を含むワークフローを「Inspect（読み取り専用で状況確認）→ Call（ユーザー確認後に実行）」の2段階で設計する。

```text
Phase 1（Inspect）: 対象データの確認 → 影響範囲の把握 → 読み取り専用
Phase 2（Call）:     ユーザー確認 → 実行
```

### チェック項目

- [ ] 破壊的操作を含む場合、読み取り専用フェーズと実行フェーズが分離されているか
- [ ] Phase 1 が明示的に「読み取り専用」と制約されているか
- [ ] Phase 2 の前にユーザー確認が組み込まれているか
- [ ] 影響範囲の把握が実行前に行われる設計になっているか

### 良い例

```markdown
## ワークフロー

### Phase 1: 調査（読み取り専用）
1. 対象ファイルを一覧取得する
2. 変更対象と影響範囲を特定する
3. 変更計画をユーザーに提示する

### Phase 2: 実行（ユーザー確認後）
4. ユーザーの承認を得る
5. 変更を実行する
6. 結果を報告する
```

### 悪い例

```markdown
## 手順
1. ファイルを検索する
2. 該当ファイルを削除する
3. 結果を報告する
```

確認フェーズなしに直接削除を実行する設計。

### 改善テンプレート

破壊的操作を含むスキルには以下の構造を組み込む:

```markdown
## Phase 1: 調査（読み取り専用）
- このフェーズではデータの変更を一切行わない
1. <対象の確認手順>
2. <影響範囲の把握手順>
3. <変更計画のユーザー提示>

## Phase 2: 実行（ユーザー確認後）
- ユーザーの明示的な承認を得てから実行する
4. <実行手順>
5. <結果の報告>
```
