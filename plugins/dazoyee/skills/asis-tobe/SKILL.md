# asis-tobe

変更に着手する前に「今どうなっていて（As-Is）、どう変わるのか（To-Be）」を比較表で示し、ユーザーと認識を揃える。
着手後に「そういう意味ではなかった」と気づくと手戻りが大きいので、ずれは表の段階で潰す。

## 流れ

```
1. As-Is を調べる（コード・設定・ドキュメントを読む）
2. 依頼から To-Be を組み立てる
3. 比較表をチャットに出す
4. AskUserQuestion で承認を取る
   - 進める → 5 へ
   - 修正したい → 指摘を反映して 3 に戻る
   - 中止 → 何も変更せずに終える
5. 変更に着手する。表と違うことをした点があれば、完了報告で明示する
```

承認が出るまでファイル編集・設定変更・コミットなどの変更作業はしない。
表を見てもらう目的は着手前の合意なので、先に手を動かすと意味がなくなる。

## As-Is は事実で書く

As-Is はコードベースや設定を実際に読んで書く。推測で埋めると、比較表そのものが誤解の元になる。
調べても分からない点は「要確認」と書き、表の下の懸念欄で何が分からないかを示す。

## 比較表の書き方

次のテンプレートで出力する。

```markdown
## As-Is / To-Be: <変更の一言要約>

<なぜ変えるのかを1〜2文で>

| 項目 | As-Is | To-Be |
|---|---|---|
| <観点> | <現状> | <変更後> |

**影響範囲**: <変更するファイル・設定・利用者など>
**懸念・トレードオフ**: <互換性、運用への影響、未確定事項など。なければ「特になし」>
```

- **項目は振る舞い・仕様の観点で立てる**。利用者から見える挙動、入出力、設定、運用手順など「何がどう変わるか」が伝わる単位にする。ファイル名や関数名は項目にせず、影響範囲に寄せる。読み手が変更の意味を掴めることを優先するため。
- **変わる項目だけを載せる**。ただし「変わると誤解されやすいが変わらない点」は、To-Be を「変更なし」として載せてよい。
- 新しく追加するものは As-Is を「なし」、削除するものは To-Be を「なし（削除）」とする。
- セルは短く保つ。説明が長くなる項目は、表の下に補足を書く。
- 変更が独立した複数のテーマにまたがるときは、テーマごとに表を分ける。

## 承認の取り方

表を出した直後に `AskUserQuestion` で確認する。

- 質問: 「この As-Is / To-Be で進めてよいですか？」
- 選択肢:
  - `この内容で進める (Recommended)` — 表の To-Be どおりに着手する
  - `修正したい` — 指摘を受けて To-Be を直し、表を出し直す
  - `中止する` — 何も変更しない

「修正したい」が選ばれたとき、または Other で指摘が来たときは、指摘を反映した表を全体ごと出し直して再び承認を取る。
差分だけを口頭で伝えると、最終的に何で合意したのかが曖昧になるため。
修正の意図が読み取れないときは、表を出し直す前に何を変えたいかを聞く。

## 変更が済んでいる場合

「今やった変更を As-Is/To-Be で見せて」のように変更後に頼まれたときは、`git diff` などから As-Is / To-Be を起こして表を出すだけにする。
すでに変更済みなので承認は取らない。
