# repo-docs

README.md・CONTRIBUTING.md・AGENTS.md・CLAUDE.md は、それぞれ読み手が違う。
読み手を混ぜると、README が開発者向けの手順で膨らむ、エージェントへの指示が人間向けの文書に埋もれる、同じ情報が複数ファイルに散って片方だけ古くなる、といった問題が起きる。
このスキルは、どの情報をどのファイルに置くかを決め、各ファイルをデファクトスタンダードの構成で書く。

## 役割分担

| ファイル | 読み手 | 答える問い | 置くもの | 置かないもの |
|---|---|---|---|---|
| README.md | 利用者（初めて見る人） | これは何で、どう使い始めるか | 概要・インストール・使い方・ライセンス・CONTRIBUTING への案内 | 開発環境の構築・コーディング規約・エージェント向けの指示 |
| CONTRIBUTING.md | 開発に参加する人間 | どう開発に参加するか | 環境構築・ビルド/テスト/lint のコマンド・規約・コミットと PR の流れ・不具合の報告方法 | 利用方法・エージェント固有の指示 |
| AGENTS.md | コーディングエージェント全般 | 作業中に何を守り、どう検証すれば完了か | 人間向けの文書には書かれない暗黙知・落とし穴・触ってはいけない場所・完了条件 | 人間向けの文書の転記・一般論 |
| CLAUDE.md | Claude Code | Claude Code 固有の差分は何か | `@AGENTS.md` の取り込みと、Claude Code にしか通じない指示 | AGENTS.md と同じ内容 |

各ファイルの標準構成とチェックリストは、扱うファイルに応じて読む。

- README.md → `references/readme.md`
- CONTRIBUTING.md → `references/contributing.md`
- AGENTS.md・CLAUDE.md → `references/agents-md.md`

## 重複させない

1つの情報の正本は1か所に置き、他のファイルからは参照する。
正本は「その情報を最初に必要とする読み手」のファイルに置く。
複製すると片方だけ更新されて食い違い、エージェントは古いほうを信じて作業してしまう。

- **開発手順**（環境構築・ビルド・テスト・lint）の正本は、リポジトリの規模によらず常に CONTRIBUTING.md に置く。人間もエージェントも使うが、先に必要とするのは参加者だから。README には書かず、リンクだけを置く。置き場所が規模で揺れると、どこが正本か読み手にも点検にも分からなくなる。
- **AGENTS.md の開発コマンド**は、「ビルドとテストは CONTRIBUTING.md の〈節名〉に従う」という参照と、変更後に必ず通すコマンド（完了条件）だけを書く。手順の全体は書かない。完了条件だけは、エージェントが参照先を読み飛ばしても検証を飛ばさないよう、AGENTS.md に直接書く。
- **共通か Claude Code 固有か**は「Codex など他のエージェントが読んでも役に立つか」で判断する。役に立つなら AGENTS.md、Claude Code のスキル・hooks・サブエージェント・設定に依存する指示だけ CLAUDE.md に置く。
- **参照の書き方**:
  - CLAUDE.md からは `@AGENTS.md` のように `@パス` で取り込む。Claude Code が起動時に展開するので、読み飛ばされない。
  - AGENTS.md には取り込み構文が通じないエージェントが多い。読むべきファイルと節を相対パスで明示する。
  - README.md・CONTRIBUTING.md の間は通常の Markdown リンクにする。

## 流れ

```
1. 調査する
2. ファイルごとに「作成」か「点検」かを決める
3. 作成 → 標準構成で書いて完了報告
   点検 → 指摘一覧を出す → 承認を得る → 修正して完了報告
```

### 1. 調査する

書く内容は推測でなく実物から取る。コマンドやツール名を推測で書くと、動かない手順書になる。

- 既存の README.md・CONTRIBUTING.md・AGENTS.md・CLAUDE.md（サブディレクトリにあるものも含む）
- 依存とコマンドの定義元: `package.json`・`pom.xml`・`build.gradle`・`pyproject.toml`・`Makefile`・`Cargo.toml`・`go.mod` など
- CI の設定（`.github/workflows/` など）。CI が実際に回しているコマンドが、検証手順の最も確かな根拠になる
- `LICENSE`・`CODE_OF_CONDUCT.md`・`SECURITY.md`・`.github/ISSUE_TEMPLATE/`・`.github/PULL_REQUEST_TEMPLATE.md`
- `git log` のコミットメッセージ（規約と文書の言語を知るため）

調べても分からないこと（ライセンス未設定、対応バージョンが不明など）は、文書に推測で書かず、プレースホルダや TODO も残さない。完了報告や指摘一覧でユーザーに確認する。

### 2. 作成か点検かを決める

- ファイルが無い → 作成。承認を待たずに書く。
- ファイルがある → 点検。承認が出るまで編集しない。
- 1回の依頼で両方が混ざってよい。

ただし、既存ファイルから内容を移して作る新規ファイル（README の開発手順を移す CONTRIBUTING.md など）は、点検の指摘一覧に載せて承認を待つ。
移す元の修正と一体の変更なので、先に作ると承認が出るまで同じ内容が2か所に並び、承認されなかったときに重複だけが残る。

依頼に含まれないファイルは、確認なしには作らない。ただし次の2つは正本の置き場所を成り立たせるのに必要なので、無ければ作成を提案する。

- **AGENTS.md**: CLAUDE.md を頼まれて AGENTS.md が無いとき。共通の内容は AGENTS.md に置く前提なので、無いと CLAUDE.md に共通の内容を書くことになり、後で Codex などを使うときに移し替える手間が生じる。
- **CONTRIBUTING.md**: 開発手順を書く必要があり CONTRIBUTING.md が無いとき（AGENTS.md から参照させる、README から開発手順を追い出すなど）。開発手順の正本は常に CONTRIBUTING.md だから。

提案は、調査を終えて何かを書き始める前に行う（質問ツールの使い方は 3b と同じ）。
AGENTS.md は複数のエージェントの挙動を変え、CONTRIBUTING.md は参加者の手順を決めるため、頼まれていないものを黙って足すと、レビューされないまま影響が広がる。
また、作るかどうかで依頼されたファイルの中身も変わるので、書いた後に聞くと書き直しになる。

断られたときは、その内容を依頼されたファイルに書く（共通の指示は CLAUDE.md に、開発コマンドは AGENTS.md に直接書く）。正本の置き場所が標準と違うことは完了報告で伝える。

リポジトリに文書の書き方の決まり（既存の AGENTS.md の指示、`docs/` の規約など）があれば、このスキルの標準構成よりそちらを優先する。

### 3a. 作成

references の標準構成に沿って書き、完了報告をする。

### 3b. 点検 → 承認 → 修正

既存の文書には、書いた人の意図や、リポジトリの外の事情が反映されていることがある。いきなり書き換えず、指摘を先に見せて合意を取る。

references のチェックリストと「重複させない」の観点で点検し、次の形式で指摘一覧を出す。

```markdown
## 指摘一覧

| # | ファイル | 種別 | 内容 | 対応案 |
|---|---|---|---|---|
| 1 | README.md | 置き場所違い | 開発環境の構築手順が README にある | CONTRIBUTING.md を新規作成して移し、README からはリンクする |
```

移動先のファイルを新しく作る場合は、対応案に「新規作成」と明記する。承認がそのファイルの作成も含むことが読み手に分かるようにするため。

種別は次のいずれか。

- **不足**: 標準構成で必要な節が無い
- **重複**: 同じ情報が複数のファイルにある
- **置き場所違い**: 読み手の違うファイルに書かれている
- **不一致**: 実物（マニフェスト・CI・ディレクトリ構成）と食い違っている
- **陳腐化**: 後述の「陳腐化する記述」に当たる
- **冗長**: 読み手の役に立たない記述（一般論、エージェントが言われなくても守ること）

指摘一覧を出したら、質問ツール（Claude Code なら `AskUserQuestion`、Codex なら `request_user_input`）があれば使い、無ければ平文で聞いて回答を待つ。
選択肢は「すべて対応する」「番号を選んで対応する」「対応しない」の3つにする。
承認が出るまでファイルを編集しない。

## 書き方の共通ルール

- **言語**: 既存の文書とコミットメッセージの言語に合わせる。手掛かりが無ければ日本語で書く。
- **陳腐化する記述を書かない**: 「現在は」「〇月時点で」などの時制表現、進捗・TODO、個別の issue や依頼者への言及は書かない。バージョン番号やファイル数は直書きせず、定義元のファイル（`.nvmrc`・`pom.xml` など）を示す。書いた時点でしか正しくない記述は、気づかれないまま嘘になるから。
- **コマンドはそのまま動く形で書く**: コードブロックに入れ、コピーして実行できる形にする。実物で確認できたものだけを書く。
- **実在しないものを書かない**: バッジ・URL・連絡先・ライセンス名を推測で作らない。
- **AGENTS.md と CLAUDE.md は短く保つ**: 毎回エージェントのコンテキストに読み込まれるため、長いほど他の指示が埋もれる。エージェントが言われなくても守る一般論（「読みやすいコードを書く」など）は削る。

## 完了報告

次を報告する。

- 作成・修正したファイル
- 置き場所の判断（どの情報の正本をどのファイルに置き、どこから参照したか）
- 調べても分からず、書かなかった事項（ユーザーに確認したいこと）
