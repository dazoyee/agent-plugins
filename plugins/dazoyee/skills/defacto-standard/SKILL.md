# defacto-standard

何かを決めるときの参考として、候補となるデファクトスタンダードを調べ、比較表と推奨案をチャットに提示する。
推測ではなく根拠を集めてから提示する。学習データ上の古い推奨で決めると、現在の標準や保守状況を取り違えるため。

## 自動で使う場面

- ライブラリ・フレームワークの選定、設定ファイルやディレクトリ構成の決め方、ドキュメントや CI の構成など、後から変えにくい決めごとが会話に出て、まだ決まっていないときは自動で調査する。
- 既に決まっている事項や、既存プロジェクトの規約が明らかな場合は使わない。
- 変数名や一文の書き方など瑣末な選択や、軽い相談では使わない。調査は時間がかかるため、軽い相談のたびに走らせない。
- 調べるべきか迷うときは、調査を始める前に「デファクトを調べますか」と一言聞く。

## 流れ

```
1. 論点を特定する
2. 既存プロジェクトの規約を確認する
3. 候補を洗い出す
4. 根拠を集める
5. 比較表と推奨案をチャットに出して終わる
```

決定は取らない。相談だけのときに煩わしいため、AskUserQuestion は使わない。

## 既存規約の確認

既存プロジェクトに規約があれば、それを最優先する。デファクトと乖離している場合は指摘に留め、既存規約を無断で置き換えない。
コードベースから分かることはユーザーに聞かず、Grep / Read / Glob で調べる。

## 候補の優先順位

上から順に検討し、採用できる最上位の候補を推奨する。

1. 標準仕様（RFC・ISO・言語公式の仕様や標準ライブラリ）
2. 利用中のフレームワーク・ツールが公式に推奨する方法
3. エコシステムで広く採用されているもの（採用実績と保守状況で判断）
4. 自作

上位の候補を外す場合は理由を示す。
広く使われていることと今回の状況に合うことは別に評価する。普及している慣行を、そのまま今回の最適解とは扱わないため。

## 根拠の集め方

- 公式ドキュメントを WebFetch で読む。
- WebSearch で採用実績を確認する。公式サイト・GitHub・パッケージレジストリ・著名プロジェクトの採用例・公開調査を使う。
- context7 MCP が使えるときは、現行版のドキュメントを引く。
- 根拠には URL を付ける。確かめられなかった事項は「未確認」と書く。
- 候補は 2〜4 件に絞る。

## 比較表

次のテンプレートで提示する。

```markdown
## デファクトスタンダード調査: <論点>
<前提: 既存規約の有無を1〜2文>
| 候補 | 階層 | 採用実績・保守状況 | 長所 | 短所 | 今回への適合 | 根拠 |
|---|---|---|---|---|---|---|
| ... | ... | ... | ... | ... | ... | [資料](URL) |

**推奨**: <候補> — 普及度: <根拠を簡潔に> / 今回への適合: <要件・安全性・運用面の理由を簡潔に>
**上位の階層を外した理由**: <なければ「なし」>
**未確認事項**: <なければ「なし」>
```

## 注意

推奨は示すが、ユーザーが別案を選んでも受け入れる。表のセルは短く保ち、長い説明は表の下に書く。
