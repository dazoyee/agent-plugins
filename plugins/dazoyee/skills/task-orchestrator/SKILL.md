# Task Orchestrator

複数の作業を含む依頼を、**作業本体をサブエージェントに委譲**して捌くためのスキル。あなた（メインのClaude）は
オーケストレーターとして、分解・委譲・統合・判断に徹する。コードやファイルの重い読み書きはワーカーに任せる。

なぜこうするのか。マルチエージェントはチャット単体の約15倍のトークンを消費するが、性能分散の8割はトークン量で説明でき、
価値の高いタスクを並列化すれば調査・実装時間を最大9割短縮できる（Anthropic, multi-agent research system）。
逆に、単純な作業を無理に分割すると調整コストと重複作業だけが増える。だから「分割する価値があるか」を最初に判断する。

## いつ使い、いつ使わないか

オーケストレーションが効くのは、**独立に進められる作業単位が複数あり、それぞれがそれなりに重い**とき。
逆に次のケースでは委譲せず自分で直接やるか、その領域の専門的なやり方に任せるほうが速く、安い:

- 単一の連続した作業（分割すると文脈が分断されて非効率）
- 1ファイルの小さな編集、事実1件の確認
- 作業同士が密結合で、常にお互いの途中結果を参照し合う必要がある
- **作業単位が1つだけ**のとき（たとえ重い調査でも、単一トピックなら分解の余地がない）
- **すでに完了した成果物を評価・手直しするだけ**のとき（新規作業の分解ではない）

迷ったら「この作業を別々の人に渡して、最後に報告を合わせて成立するか?」で判断する。成立しないなら単一で進める。

このスキルは特定のドメインに依存しない。調査・レビュー・実装など各作業の**中身のやり方**は、その領域の専門的な手順に委ねる（後述のとおりワーカーは自分でスキルを参照できる）。ここで扱うのは、あくまで**複数作業をどう分解・委譲・統合するか**という一段上の段取りだけ。単一の重い作業が1件あるだけなら、このスキルではなくその作業に適した進め方を選ぶ。

## コアループ

1. **分解** — 依頼を独立した作業単位に切り出す
2. **依存判定** — 各単位の依存関係を見て、並列できるもの／順番が要るものを分ける
3. **計画の可視化** — `TaskCreate` でタスクリストを作り、ユーザーに実行計画が見えるようにする
4. **委譲** — 独立な単位は同一メッセージ内で複数の Agent を同時起動、依存があるものは前段の結果を待って起動
5. **統合** — 各ワーカーの構造化された結果を集約し、総括レポートとして返す

### 1. 分解と粒度

作業の重さに合わせて分割の細かさを変える。細かく割りすぎると重複と調整が増え、粗すぎると1ワーカーが枯渇する。

| タスクの性質 | サブエージェント数の目安 |
|---|---|
| 単純な事実確認・軽い作業 | 委譲せず自分で、または1エージェント |
| 直接比較・2〜3観点のレビュー | 2〜4エージェント |
| 広範囲の調査・多ファイル実装 | 3〜5エージェント（必要なら段階分割） |

**同時に走らせるのは3〜5が上限の目安**。6以上に増やすと調整オーバーヘッドが利益を食いつぶす。
それ以上の作業量があるときは、バッチに分けて逐次オーケストレーションする（例: 5件ずつ実行し、各バッチ後に統合・確認）。

数十件規模の一括処理や、fan-out/pipeline を決定論的に回したいときは、Agent ツールの手動オーケストレーションより
Workflow ツール（ユーザーの明示的な opt-in が前提）のほうが向く。その場合はこのスキルではなく Workflow を検討する。

### 2. 依存判定

- **独立（同じファイルを触らない・互いの結果を必要としない）→ 並列**。同一メッセージで複数 Agent を起動する。
- **依存あり（後段が前段の成果物を必要とする）→ 直列**。前段の結果を受け取ってから後段を起動する。
- **同一ファイルを書き換える複数ワーカーは並列にしない**。上書き事故が起きる。どうしても並列が必要なら
  `isolation: "worktree"` で各ワーカーを隔離するか、ファイル所有権を1ワーカーに寄せる。

依存関係が自明でなく、実行順で結果が大きく変わりそうなときは、分解案をユーザーに提示して確認してから走らせる。

### 3. 委譲プロンプトの書き方

サブエージェントは会話履歴を引き継がない。渡した内容がすべて。曖昧な指示（「〇〇について調べて」だけ）は
ワーカーの誤解や、他ワーカーとの重複作業を招く。各委譲プロンプトに次の4要素を必ず含める:

1. **目的** — このワーカーが達成すべきこと（1つに絞る。1ワーカー1責務）
2. **出力フォーマット** — 何を、どういう構造で返すか（後述の「構造化して返させる」を参照）
3. **使ってよいツール・情報源** — どこを見るか、どのMCP/ファイルを参照するか。参照ファイルは3〜5件に絞る
4. **タスク境界** — やること・やらないこと。他ワーカーの担当領域には手を出さないと明示する

調査に必要な文脈は、ワーカーに大量ファイルを読ませるのではなく、**あなたが既に持っている仕様・制約を
プロンプトに直接書いて渡す**。ワーカーが自由に読み漁るとコンテキストが枯渇して本題に入れなくなる。

ワーカーはあなたと同じくスキルを参照できる。だから作業の中身のやり方まで手取り足取り書く必要はない。
専門性が要る作業単位（特定領域の調査・レビュー・実装など）には「**適したスキルがあれば使ってよい**」と一言添えれば、
ワーカーが自分でその領域の手順を呼び出して質を上げる。オーケストレーター側で個別スキル名を管理する必要はない。

### 4. 構造化して返させる

ワーカーの最終テキストがそのまま返り値になる。あなたがそれを読んでコンテキストが膨らむのを防ぐため、
**成果物そのものではなく、要約・差分・要点を構造化して返させる**。

- 実装ワーカー → 「変更したファイルのパス一覧＋各変更の1行要約＋ビルド可否」を返す。差分全文は返させない。
- 調査ワーカー → 「結論＋根拠（出典/ファイルパス:行）＋要確認事項」を Markdown で返す。
- 定型の構造が必要なら、返り値のテンプレートをプロンプトに明示する。

大きな成果物（生成ファイル等）はワーカーに保存させ、あなたはパスと要約だけ受け取る。全文が要るときだけ後で読む。

### 5. 統合

全ワーカーの結果が揃ったら、あなた自身は新規のコードを書かず、統合と判断に専念する:

- 各結果を突き合わせ、矛盾・抜け・重複がないか確認する
- 中間手順ではなく**最終状態が要件を満たすか**で評価する（ワーカーは別経路で同じゴールに達しうる）
- 総括レポートを返す（後述のテンプレート）。必要なら追加の委譲を1ラウンド回す

## 進捗の可視化

着手時に `TaskCreate` で作業単位ごとのタスクを登録し、起動時に `in_progress`、完了時に `completed` に更新する。
ユーザーが「今どのフェーズにいるか」を把握でき、見落としも防げる。

## 総括レポートの構成

作業完了時は、この構成でまとめて返す:

```
## 実行サマリー
- 分解した作業単位と、それぞれの担当（並列/直列の別）

## 各作業の結果
### [作業1]
- 結論 / 成果物のパス / 要点

### [作業2]
...

## 統合所見
- 全体としての結論、矛盾や要確認点、残タスク
```

作業完了時は、ユーザーのグローバル設定に従いデスクトップ通知を実行する:
`bash ~/.claude/scripts/notify.sh "Claude Code" "<実行した具体的な作業内容>"`

## アンチパターン

- **過剰な並列化** — 単純な作業に多数のワーカーを割り当てる。調整コストだけが増える。
- **不要な直列化** — 独立な作業を1つずつ順番に処理する。並列にできるものは同一メッセージで同時起動する。
- **曖昧な委譲** — 目的・境界を書かずに投げる。ワーカーが誤解し、他ワーカーと同じ作業をする。
- **コンテキスト肥大** — ワーカーの成果物全文を自分で読む。要約・パスだけ受け取る設計にする。
- **同一ファイルの並列編集** — 上書き事故。ワークツリー隔離か所有権の集約で回避する。
- **無理な複雑化** — 単一エージェントで足りるものを分割する。複雑性は実証的に改善がある場合だけ足す。

## 例

**例1: 独立3作業の並列委譲**

Input: 「認証まわりのセキュリティ調査と、キャッシュ層の性能レビューと、ユーティリティの静的解析をやって」
→ 3作業は独立。同一メッセージで3つの Agent を起動し、各ワーカーに目的・出力フォーマット・参照範囲・境界を明示。
　結果を統合して総括レポートを返す。

**例2: 依存のある直列＋並列の混在**

Input: 「新しいAPIを5本実装して、その後まとめてテストを書いて」
→ 実装5本は互いに独立なら並列（ただし同一ファイルを触るものは隔離 or 集約）。テストは実装結果に依存するので、
　実装が揃ってから起動する。実装が10本を超えるならバッチ分割し、各バッチ後にビルド確認してから次へ。

**例3: 委譲しない判断**

Input: 「この関数の引数名を変えて」
→ 単一の小さな編集。委譲せず自分で直接行う。
